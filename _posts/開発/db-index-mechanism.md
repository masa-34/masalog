「インデックスを貼ると検索が速くなる」というのはよく聞きますが、実際に中でどんなことが起きているのかを図でイメージしながら整理したメモです。
`EXPLAIN`の使い方や`CREATE INDEX`の構文は[別記事](/posts/sql-basic-query)で触れているので、ここでは「なぜ速くなるのか」という仕組みの部分にフォーカスします。

## インデックスがないとどうなるか

インデックスがない状態で`WHERE`検索をすると、DBはテーブルの先頭から1行ずつ全件を確認していきます。これを**フルスキャン（Seq Scan）**と呼びます。

```text
users テーブル（10万行）
┌────┬──────┬─────┐
│ id │ name │ age │
├────┼──────┼─────┤
│ 1  │ 田中 │ 28  │ ← 1行目から順番に
│ 2  │ 佐藤 │ 34  │   「age = 40 か？」を
│ 3  │ 鈴木 │ 22  │   全部チェックしていく
│ …  │  …   │  …  │
│100000 │ … │ …  │ ← 最後の行までたどり着く
└────┴──────┴─────┘
```

たとえば`SELECT * FROM users WHERE age = 40;`を実行すると、目的の行が1件しかなくても、10万行すべてに目を通す必要があります。本を最初のページから1枚ずつめくって特定の単語を探すようなもので、データ量が増えるほど時間もそのまま比例して増えていきます。

## 本の「索引」と同じ発想

紙の本で特定の単語を探すとき、最初のページから読むのではなく、巻末の索引（さくいん）で単語を引いて該当ページに一気にジャンプするはずです。

```text
索引（インデックス）           本文（テーブル）
┌───────────┬──────┐         ┌──────────────┐
│ 「あ」    → 12ページ │  ───▶  │ 12ページの内容 │
│ 「か」    → 45ページ │  ───▶  │ 45ページの内容 │
│ 「さ」    → 88ページ │  ───▶  │ 88ページの内容 │
└───────────┴──────┘         └──────────────┘
```

DBのインデックスもこれと同じ考え方です。「列の値」と「その値を持つ行の場所（ポインタ）」をセットにした、探しやすい形の索引データを別に作っておきます。検索時はまず索引を引いて場所を特定し、そこにピンポイントでアクセスする、という2段階の動きになります。

## 中身はほぼ「木構造（B-Tree）」

多くのDBでは、インデックスの索引データは**B-Tree（B木）**と呼ばれる木構造で保持されています。値が小さい順に整理された木を上からたどっていくイメージです。

```text
                  [ 30 | 60 ]                ← ルート
                 /      |      \
         [10|20]     [40|50]     [70|90]     ← 中間ノード
         /  |  \      /  |  \      /  |  \
       ...  ... ...  ... ... ...  ... ... ...  ← 葉ノード（実データへのポインタ）
```

`age = 45`を探す場合の流れは、たとえばこうなります。

1. ルートを見る → `30`より大きく`60`より小さい → 真ん中の枝へ進む
2. `[40|50]`のノードを見る → `40`より大きく`50`より小さい → 該当の葉ノードへ進む
3. 葉ノードから実データの場所（ポインタ）を取得し、テーブルの該当行を読みにいく

木の各段階で候補を大きく絞り込めるため、10万行あっても「木の深さ分（数段）」比較するだけで目的地にたどり着けます。データ量が10倍に増えても、木の深さはほんの少ししか増えないため、フルスキャンのように検索時間が比例して伸びていくことがありません。

## Seq ScanとIndex Scanの体感差

イメージしやすいように、10万行から特定の1件を探すケースで比較すると次のような違いになります。

| 方式 | やること | データ量が増えたときの傾向 |
|------|----------|----------------------------|
| Seq Scan（インデックスなし） | 全行を1件ずつ確認 | 行数に比例して遅くなる |
| Index Scan（インデックスあり） | 木を数段たどって直接アクセス | 行数が増えても遅くなりにくい |

実際に自分の環境で`EXPLAIN ANALYZE`を実行すると、インデックスの有無で`Seq Scan`と`Index Scan`が切り替わり、実行時間（`Execution Time`）が変わる様子を確認できます。

## インデックスは万能ではない

ここまでだと「とりあえず全部の列に貼っておけばよさそう」と思うかもしれませんが、インデックスにはコストもあります。

- **書き込みが遅くなる**：`INSERT`・`UPDATE`・`DELETE`のたびに、テーブル本体だけでなく索引側の木構造も更新する必要がある
- **容量を消費する**：索引データ自体もディスクを使う
- **効果が薄いケースがある**：値の種類が数種類しかない列（性別や真偽値など）は、木で絞り込んでもあまり候補が減らないため効果が小さい

そのため実務では、「検索・`JOIN`の条件によく使われる列」かつ「値の種類が豊富な（カーディナリティが高い）列」を優先してインデックスを検討する、というのが基本方針になります。

## まとめ

- インデックスがないと、DBは`WHERE`条件のたびにテーブルを先頭から全件確認する（Seq Scan）
- インデックスは本の索引と同じ発想で、「値→場所」の対応表を検索しやすい形（多くはB-Tree）で別に持たせたもの
- B-Treeは木を数段たどるだけで目的地に近づけるため、データ量が増えても検索速度が落ちにくい
- 一方で書き込みコストや容量を消費するため、よく検索条件に使われ、かつ値の種類が豊富な列に絞って貼るのが基本
- 実際に効いているかどうかは、`EXPLAIN`や`EXPLAIN ANALYZE`で`Seq Scan`か`Index Scan`かを見て確認できる

「なぜ速くなるのか」の仕組みをイメージできると、どの列にインデックスを貼るべきかの判断もしやすくなりそうです。
