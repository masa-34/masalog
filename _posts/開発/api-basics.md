「APIを叩く」「APIキーを設定する」という言葉は普段からよく使っているのに、いざ仕組みを説明しようとすると意外と曖昧だったので、自分の理解の整理も兼ねてまとめておきます。

## APIとは何か

API（Application Programming Interface）とは、**あるソフトウェアの機能を、別のソフトウェアから使えるようにするための「窓口」**のことです。

例えば天気アプリは、自分で気象データを持っているわけではなく、気象庁や気象データ提供元の**API**にリクエストを送り、返ってきたデータを画面に表示しているだけ、ということが多いようです。

```text
天気アプリ（クライアント） --- リクエスト ---> 気象データAPI（サーバー）
天気アプリ（クライアント） <-- レスポンス --- 気象データAPI（サーバー）
```

自分でゼロから作らなくても、他社・他システムの機能をそのまま利用できるのがAPIの一番の価値だと理解しました。

## APIの代表的な種類

一口にAPIといっても、設計思想の異なるいくつかの種類があるようです。調べて分かった代表的なものを挙げます。

| 種類 | 特徴 | よく使われる場面 |
|------|------|------------------|
| **REST API** | URL（エンドポイント）とHTTPメソッドで操作を表現する。JSON形式のやり取りが主流 | Web/モバイルアプリの裏側の大半 |
| **GraphQL** | 1つのエンドポイントに対し、クライアントが「欲しいデータの形」をクエリで指定する | 画面ごとに必要な項目が違う複雑なアプリ |
| **gRPC** | Googleが開発。バイナリ形式（Protocol Buffers）で高速通信。型定義を共有して使う | マイクロサービス間の内部通信 |
| **SOAP** | XMLベースの古典的な規格。厳格な仕様（WSDL）を持つ | 金融・官公庁系など歴史あるシステム |
| **WebSocket** | 一度接続すると双方向でリアルタイムにやり取りできる | チャット、株価などのリアルタイム更新 |

普段のWeb開発で一番よく見かけるのは**REST API**なので、この記事でも以降はRESTを中心にまとめます。

## REST APIの基本: リクエストとレスポンス

REST APIは、HTTPという通信プロトコルの上に成り立っています。基本の考え方はシンプルで、**「何に対して」「何をするか」をURLとHTTPメソッドで表現する**というものでした。

```text
GET    /users        → ユーザー一覧を取得する
GET    /users/1      → id=1のユーザーを取得する
POST   /users        → 新しいユーザーを作成する
PUT    /users/1      → id=1のユーザーを更新する（全体置き換え）
PATCH  /users/1      → id=1のユーザーを更新する（一部だけ）
DELETE /users/1      → id=1のユーザーを削除する
```

`/users` のようなURLを**エンドポイント**、`GET`/`POST`などを**HTTPメソッド**と呼びます。この組み合わせだけで、意外と多くの操作を表現できるんだなというのが素直な感想です。

### 実際のやり取りのイメージ

例えば `GET /users/1` を送ると、サーバーからはこんなレスポンスが返ってきます。

```text
リクエスト:
GET /users/1 HTTP/1.1
Host: api.example.com
Authorization: Bearer xxxxxxxx

レスポンス:
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 1,
  "name": "山田太郎",
  "email": "yamada@example.com"
}
```

レスポンスの先頭についている `200 OK` は**ステータスコード**と呼ばれ、リクエストの結果を表します。代表的なものはこの通りです。

| コード帯 | 意味 | 代表例 |
|----------|------|--------|
| 2xx | 成功 | `200 OK` / `201 Created` |
| 3xx | リダイレクト | `301 Moved Permanently` |
| 4xx | クライアント側のエラー | `400 Bad Request` / `401 Unauthorized` / `404 Not Found` |
| 5xx | サーバー側のエラー | `500 Internal Server Error` |

## 認証: 誰がAPIを叩いているかを確認する

APIは誰でも自由に呼べてしまうと困るものが多いので、多くの場合「呼び出しているのが誰か」を確認する仕組みが付いているようです。代表的な方式はこちら。

- **APIキー**: 発行された固定の文字列をリクエストに含める、シンプルな方式
- **Bearerトークン / OAuth2**: ログイン後に発行される一時的なトークンを `Authorization: Bearer xxxx` の形でリクエストに添える方式。有効期限があり、漏洩時の影響を抑えやすい
- **Basic認証**: ユーザー名とパスワードをそのままエンコードして送る、簡易的な方式

先ほどの例にあった `Authorization: Bearer xxxxxxxx` は、まさにこのトークンを使った認証のヘッダーでした。

## データ形式: 主にJSONでやり取りする

今のAPIの多くは、リクエストボディやレスポンスの中身に**JSON**というデータ形式を使っています。

```json
{
  "name": "山田太郎",
  "age": 28,
  "hobbies": ["読書", "登山"]
}
```

JSONはテキストベースで人間にも読みやすく、ほとんどのプログラミング言語で標準的に扱えるので、事実上の共通言語みたいな立ち位置になっているみたいです（SOAPなど一部の古い規格ではXMLが使われます）。

## まとめ：APIとは？

- APIは**「他のソフトウェアの機能を呼び出すための窓口」**で、代表的な種類にはREST・GraphQL・gRPC・SOAP・WebSocketなどがある
- 今主流の**REST API**は、URL（エンドポイント）とHTTPメソッド（GET/POST/PUT/PATCH/DELETE）の組み合わせで操作を表現する
- レスポンスには**ステータスコード**が付いていて、結果の成否や種類を表す
- 多くのAPIは**APIキーやトークン**による認証で、呼び出し元を確認している
- データのやり取りには**JSON**が使われることが多い

「APIを叩く」という言葉の中身は、突き詰めると「決まった形式のリクエストを送り、決まった形式のレスポンスを受け取る」というシンプルなやり取りの積み重ねだったんだなと理解できました。
