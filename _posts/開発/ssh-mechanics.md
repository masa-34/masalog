`ssh user@host` と打つだけで普通にリモートサーバーに入れてしまいますが、裏側で何が起きているのかちゃんと説明しろと言われると意外と怪しかったので、自分の理解の整理も兼ねてまとめてみます。

## SSHが解決している3つの問題

SSH（Secure Shell）は、信頼できないネットワーク越しでも安全にリモート操作できるようにするための仕組みです。ざっくり言うと、次の3つを解決しています。

1. **盗聴されない**（通信を暗号化する）
2. **なりすましサーバーに繋がない**（サーバーの身元を確認する）
3. **なりすましユーザーを弾く**（クライアントの身元を確認する）

接続確立の流れも、この3つに対応する形で3段階になっているようです。

## 接続確立までの流れ

`ssh` コマンドを実行してからシェルが使えるようになるまで、大まかに次の順番で処理が進みます。

```text
1. TCP接続の確立（通常ポート22）
2. バージョンネゴシエーション（お互いのSSHバージョンを確認）
3. 鍵交換（Diffie-Hellman）で「セッション鍵」を共有
4. ホスト鍵によるサーバー認証（known_hosts の確認）
5. ユーザー認証（公開鍵認証 or パスワード認証など）
6. 認証後、セッション鍵で暗号化された通信路が使える状態になる
```

ここで「なるほど」と思ったのが、**4のサーバー認証と5のユーザー認証は、3で作られた暗号化通信路の「上」で行われる**という点です。鍵交換が終わる前は安全な通信路がまだないので、そもそも認証もできない、という順番になっているのは理にかなっています。

## ステップ1: 鍵交換でセッション鍵を作る（暗号化の準備）

最初に行われるのが**鍵交換（Key Exchange）**です。代表的なアルゴリズムは Diffie-Hellman（DH）や、より新しい楕円曲線版の ECDH。

このあたりを調べていて面白いなと思ったのが、**事前に何も共有していない2者が、盗聴者に見られている通信路上でも、第三者にはわからない共通の秘密（セッション鍵）を作れる**という点です。

```text
クライアント                              サーバー
    |                                        |
    |------ 鍵交換用のパラメータを送信 ------->|
    |<----- 鍵交換用のパラメータを受信 --------|
    |                                        |
    |  （それぞれが自分だけの秘密値を使って計算）  |
    |                                        |
    |==== 両者とも同じセッション鍵を導出 ====|
```

このセッション鍵は接続ごとに使い捨てで、以降の通信はすべてこの鍵を使った共通鍵暗号（AESなど）で暗号化されます。公開鍵暗号は計算コストが高いので、実際の大量データのやり取りには使わず、「最初に安全な共通鍵を作るためだけ」に使う、という役割分担になっているようです。

## ステップ2: ホスト鍵でサーバーの身元を確認する

暗号化通信路ができたら、次は「本当に繋ぎたかったサーバーに繋がっているか」を確認します。これがホスト鍵による**サーバー認証**です。

サーバーは自分の秘密鍵で署名したデータをクライアントに送り、クライアントは対応する公開鍵（サーバーのホスト鍵）でそれを検証します。ここで使われるのが、初回接続時によく見るあのメッセージでした。

```text
The authenticity of host 'example.com (203.0.113.10)' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

ここで `yes` と答えると、そのホスト鍵が `~/.ssh/known_hosts` に記録されます。次回以降の接続では、サーバーから送られてくる鍵が `known_hosts` の内容と一致するかを自動でチェックし、**一致しない場合は「中間者攻撃の可能性」として強い警告を出して接続を拒否**する、というのが `Host key verification failed` の正体でした。

## ステップ3: 公開鍵認証でクライアントの身元を証明する

サーバー側の確認が終わったら、今度はサーバーがクライアント（ユーザー）を確認する番です。パスワード認証もありますが、より安全なのが**公開鍵認証**です。

これも調べてみると、「秘密鍵を送る」のではなく「秘密鍵を持っていることを証明する」仕組みになっていました。流れはこんな感じです。

```text
1. クライアントは事前に鍵ペアを作成
     - 秘密鍵: ~/.ssh/id_ed25519（自分だけが持つ・外に出さない）
     - 公開鍵: ~/.ssh/id_ed25519.pub（サーバーの ~/.ssh/authorized_keys に登録）

2. 接続時、サーバーはクライアントにチャレンジ（ランダムなデータ）を送る

3. クライアントは秘密鍵でそのチャレンジに署名して返す

4. サーバーは authorized_keys に登録された公開鍵で署名を検証
     → 検証できれば「秘密鍵の持ち主に間違いない」と判断し、認証成功
```

このやり取りの間、秘密鍵そのものはネットワーク上を一切流れません。**「秘密鍵を提示せずに、秘密鍵を持っていることだけを証明できる」**のが公開鍵暗号を使った認証の面白いところだと思います。パスワード認証と違って総当たり攻撃にも強く、秘密鍵さえ漏れなければ突破が困難、というのも納得です。

## 認証後: 暗号化されたセッションの開始

ユーザー認証まで完了すると、ステップ1で作った共通鍵暗号を使ってシェルの入出力・ファイル転送（`scp`/`sftp`）・ポートフォワーディングなどがすべて暗号化された状態でやり取りされます。ログイン後に打つコマンドの結果も、全部この暗号化通信路を通っているということになります。

## まとめ：SSHの仕組みとは？

- SSHの接続確立は **「①鍵交換で暗号化路を作る → ②ホスト鍵でサーバーを確認 → ③公開鍵認証でユーザーを確認」** の3段階
- ①では公開鍵暗号（DH/ECDH）を使い、以降の通信用に軽量な共通鍵（セッション鍵）を導出する
- ②の `known_hosts` は「前に会ったサーバーと同じか」を検証する仕組みで、変化を検知すると強く警告してくれる
- ③の公開鍵認証は「秘密鍵を送らずに、秘密鍵の所持を証明する」チャレンジ・レスポンス方式
- 秘密鍵（`id_ed25519` など拡張子なしの方）は**絶対に他人やサーバーに渡さない**のが大前提

普段は数秒で終わる `ssh` コマンド1つの裏側に、これだけの手順が詰まっていると分かると、見え方が少し変わってきます。
